# Commerce foundations — local schema contract

Migration: `supabase/migrations/20261023132803_commerce_foundation.sql`, generated by Supabase CLI `migration new commerce_foundation`. This document describes local source and disposable-engine checks, not a production migration or commercial approval.

## Scope and reuse

The migration only adds five empty private tables, their indexes, guards and `admin_save_commerce_record`. It does not import the forty catalogue drafts, activate products, change existing prices, adjust inventory, create supplier orders or modify Checkout/webhook behavior.

Existing `suppliers` is the supplier directory. `supplier_products` remains its editable discovery association, not a verified offer: `admin_save_supplier` deletes and recreates those associations. New offers reference `suppliers` directly, never a cascading directory association. Existing `product_supplier_data` remains the legacy one-product projection and is not populated from offers.

Existing `orders`, `order_items`, `supplier_orders`, `supplier_order_items`, `order_tracking_events`, `inventory_movements` and `returns` are retained. No duplicate order/stock system, procurement execution, agent task engine or immutable order snapshot is implemented by this first migration. In particular, offer records are editable with audit; they are **not** immutable commercial snapshots.

## Tables

All tables have UUID identifiers (association table has a composite key), `created_at`, `updated_at` and RLS enabled. No permissions or policies are granted to `PUBLIC`, `anon` or `authenticated`. The backend `service_role` has explicit table CRUD and RPC execution; the RPC additionally checks the current database profile of the supplied actor with existing `private.assert_admin`. A commerce agent record never grants an account the admin role or authority to purchase.

| Table | Contract |
| --- | --- |
| `commerce_agents` | Required existing `profile_id`, name, role `sourcing/catalogue/pricing/orders/supervisor`; `is_active=false` by default. This is responsibility metadata, not a worker connection. |
| `product_variants` | Required product, SKU, name, integer `price_cents`; attributes object; EUR; draft, stock 0, unverified, requires vehicle by default. `(product_id,sku)` unique. At most one **active** default per product. |
| `supplier_offers` | Required variant, existing supplier, supplier SKU, supplier variant and HTTPS URL without credentials. Pending/unknown by default. One primary offer per variant, including pending offers. No availability or cost is inferred from existence. |
| `shipping_rates` | Required offer, uppercase two-letter country, mode and upper quantity bound; lower bound defaults to 1. Postal prefix defaults to empty and accepts ASCII letters/digits/spaces/hyphens, maximum 20 characters. EUR amounts concern the **whole line quantity**, not each unit. |
| `variant_compatibilities` | Explicit links to existing `product_compatibilities`, with composite primary key. Both sides must have the same product. No rule, vehicle, range or verification is invented. |

`supplier_offers` costs are denominated in its stated EUR/USD/GBP/CNY currency; `fx_rate`, its evidence and expiry are stored separately. The schema does not assume a conversion rate or calculate a quote. Variant and shipping prices are EUR. All money fields are integer minor units, from 0 to 2,000,000,000; `null` means unknown, **not zero**. Recoverable tax requires the corresponding gross cost to be known and cannot exceed it. This is intentionally stricter than merely comparing two present API values.

Stock is bounded 0–100,000; available supplier quantity and MOQ are bounded 1,000,000 (availability quantity may be 0). Quantity bands are 1–1,000,000 inclusive. Preparation/delivery components are nullable integers 0–730; a known maximum cannot precede a known minimum. FX is positive, at most 1,000,000, numeric `(20,10)`. Evidence fields are nullable nonblank references up to 1,000 characters; storing a reference does not authenticate its content.

`shipping_rates.goods_tax_bps` and `shipping_tax_bps` are destination-specific nullable integers 0–10,000. They are not inherited from `product_variants.sale_tax_bps`; missing destination taxes must block downstream quoting. Zero is an explicitly stored zero rate, not a fallback. Sale revenue, goods tax and shipping tax require separate computation in the quoting service, outside this migration.

## RPC

`admin_save_commerce_record(p_actor uuid, p_kind text, p_id uuid, p_data jsonb, p_expected timestamptz default null) -> jsonb`

`p_kind` is exactly `agent`, `variant`, `offer` or `shipping_rate`. `p_data` must be a flat JSON object containing only the applicable table's writable columns; variant data may additionally contain `compatibility_ids`. `id`, `created_at`, `updated_at`, unknown fields and association-row editing are not accepted in JSON. Nested variant attribute values must be strings, maximum 30 entries; keys max 100 and values max 500 characters. Compatibility lists are UUID arrays, maximum 100, without duplicates.

Creation uses `p_id=null`, `p_expected=null` and conservative defaults. Updates lock the existing row, require its exact `updated_at`, preserve omitted fields and reject a stale or missing timestamp with SQLSTATE `40001`. An explicit JSON null remains null and must satisfy database nullability. Product identity on a variant, supplier/variant identity on an offer, and offer identity on a shipping rate are immutable; create a new record instead of silently reassigning history.

The returned object is the saved table row. A returned variant also contains sorted `compatibility_ids`. An omitted compatibility list during update preserves the links; an explicit list atomically replaces them. Invalid associations roll back the row update, links **and** audit insertion. Each successful RPC inserts one existing `admin_audit` entry named `commerce.<kind>.save`, recording before/after and actor. Direct backend service-role CRUD remains trusted/privileged and is not represented as a user-facing permission; application writes should use this RPC for audit and optimistic locking.

Verified offers/rates require a nonblank evidence reference. An active variant requires `is_verified=true` and evidence. If it requires a vehicle, it must also have at least one linked rule and **all** its linked rules must be verified. Same-product and active-rule integrity also have database triggers, including deferred checks after direct association deletion. A linked rule cannot be moved to another product or downgraded while required by an active variant. No rule is promoted by saving a variant.

Dates are `timestamptz`. Expiry is not a perpetual database CHECK against the clock: the quoting service must reject expired/missing required validity and FX evidence at the actual request time. Shipping bands can overlap in storage; selection must explicitly reject ambiguity instead of silently choosing a cheap rate. Primary/default uniqueness is database enforced, but neither flag authorizes sale.

## Compatibility editing caveat

The original `20260911071309_admin_backoffice.sql` implementation of `admin_save_product` deleted and reinserted all product compatibility rows. Foundation references intentionally use `ON DELETE RESTRICT`: disabling constraints or cascading those references would silently lose fitment evidence.

The additive `20261023233030_commerce_stable_fitment_save.sql` replaces that latest original RPC without modifying old migrations. It retains the same product optimistic lock, stock guard, gallery upsert, supplier merge and final publication gate. Its rule handling now preserves stable identities:

- Explicit `ProductCompatibility.id` is optional UUID input. An existing ID must belong to that exact product, cannot be reused twice, and cannot be claimed when creating another product. Explicit identity permits deliberate in-place rule edits; existing active-variant guards still reject downgrades/moves that invalidate a linked active variant.
- Existing screens may still omit IDs. Before the RPC, `CatalogStore.write_product_atomic` compares full validated public rule content with hydrated existing rules, not row order/chassis alone. Exactly one identical match restores the ID and sends the **original raw row**, preserving stored model/generation FK values and verification actor/date. Two identical candidates are ambiguous and require explicit IDs. Changed ID-less rules are never arbitrarily assigned an old identity.
- SQL independently repeats exact typed semantic matching for direct legacy RPC callers. Canonical comparison ignores only identity, product ownership, timestamps and verification actor/date; verification state, all vehicle/FK fields, arrays, phase, options and notes remain part of identity reconciliation. Unknown/different semantic content is new, not an inferred match. Duplicate new semantic content is rejected; historical duplicate rows can be retained only by their explicit distinct IDs.
- Unchanged existing rules are not updated at all. Explicitly changed rules update in place; their verified actor/time are recorded from the authenticated admin actor, never trusted from JSON. Only genuinely omitted IDs are deleted. A linked omitted rule is still blocked by FK RESTRICT, rolling back product, rules, gallery, supplier and audit changes together. Removing/replacing such a rule requires a separately explicit variant-association operation first.
- The existing `product.create`/`product.update` audit adds kept/inserted/updated/removed rule IDs. The old non-atomic existing-product writer is disabled; the HTTP editor already uses the audited atomic writer. `app/admin.py` can keep stripping IDs from hydrated legacy merge data, because exact unchanged reconciliation restores them; IDs explicitly submitted by current clients remain accepted by the schema.

These are local changes requiring release review and an authorized migration before production claims. No rule is reverified because its title or product description was edited. No variant is reassociated automatically.

## Verification and limits

Run from backend with a configured Node executable:

```powershell
node tests/commerce_database.mjs
node tests/stable_fitment_database.mjs
python -m pytest -q tests/test_stable_fitment_save.py
```

The test imports an existing `.admin-test-runtime` PGlite package from this backend or the original local backend when run from the release worktree. It installs nothing, reads no credentials and opens no network connection. It loads the existing migration chain plus this migration in disposable PostgreSQL memory, then checks real SQL constraints/RLS/grants, admin actor rejection, uniqueness, explicit zero/null costs, update locking, rollback/audit, immutable identities, same-product/verified rule links, legacy rule-delete protection and unchanged old product/order/inventory data.

Auth users/sessions are local stubs, not GoTrue or PostgREST. Sequential stale-update tests are not evidence of cross-connection concurrency behavior. Hosted database schema state, advisors, production migration application, checkout integration, pricing accuracy, real supplier proofs and commercial product validation remain outside this test and require separate authorized verification.
